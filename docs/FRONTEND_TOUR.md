# Placement Copilot — Frontend Architecture & Codebase Tour

Welcome to the frontend codebase of **Placement Copilot**. This document provides an exhaustive, interview-ready tour of the frontend: its architecture, directory structure, request lifecycle, authentication and silent token refresh mechanism, and state management conventions.

---

## 1. High-Level Architecture & Tech Stack

The frontend is a modern single-page application (SPA) built using pure **JavaScript (ES6+) and JSX**:

- **Runtime & Build**: [Vite](https://vitejs.dev/) with `@vitejs/plugin-react` for blazing-fast Hot Module Replacement (HMR) and optimized Rollup bundling.
- **Styling**: [Tailwind CSS v4](https://tailwindcss.com/) with `@tailwindcss/vite` integration for atomic, responsive styling.
- **Routing**: [React Router v7](https://reactrouter.com/) (`react-router-dom`) handling client-side routing, protected routes, and redirects.
- **Server State**: [TanStack Query v5](https://tanstack.com/query/latest) (`@tanstack/react-query`) for asynchronous data fetching, automatic caching, background polling, and optimistic/invalidation updates.
- **Client State**: [Zustand](https://github.com/pmndrs/zustand) for lightweight, predictable global client state (session auth and toast notifications).
- **Forms & Validation**: [React Hook Form](https://react-hook-form.com/) with [Zod](https://zod.dev/) resolvers (`@hookform/resolvers/zod`) for client-side schema validation.
- **Charts & Visualizations**: [Recharts](https://recharts.org/) for Placement Readiness trend sparklines, category radars, and DSA streak distributions.

## 3. How a Request Flows

Every user action that reads or mutates data follows a clean, predictable 5-step lifecycle:

```
┌─────────────────┐       ┌─────────────────┐       ┌───────────────────┐
│ React Component │ ────> │ TanStack Query  │ ────> │   API Client      │
│ (e.g. DSAPage)  │       │ (useQuery hook) │       │ (src/lib/api/...) │
└─────────────────┘       └─────────────────┘       └─────────┬─────────┘
                                                              │
                                                              ▼
┌─────────────────┐       ┌─────────────────┐       ┌───────────────────┐
│ DOM UI Update   │ <──── │ Cache & State   │ <──── │ FastAPI Backend   │
│ & Toast Notice  │       │ Invalidation    │       │ (/api/v1/...)     │
└─────────────────┘       └─────────────────┘       └───────────────────┘
```

### Detailed Lifecycle Steps:
1. **Trigger**: An event in a component (e.g., submitting an attempt in `DSATrackerPage.jsx`) triggers a TanStack Query mutation (`useMutation`).
2. **Hook Execution**: The mutation invokes the `mutationFn`, passing form parameters to the client helper method (e.g., `api.post('/dsa/attempts', payload)`).
3. **API Client Dispatch (`client.js`)**:
   - Computes full URL (`http://localhost:8000/api/v1/...`).
   - Attaches `Authorization: Bearer <token>` from in-memory store if present.
   - Attaches `credentials: 'include'` so HTTP-only session cookies accompany the request.
   - Serializes JSON body or handles `FormData` for multipart uploads (e.g. resumes).
4. **Backend Processing & Response**:
   - FastAPI routes request through authentication dependencies, verifies token, processes database operations, and returns JSON.
5. **Cache Invalidation & UI Feedback**:
   - On mutation success, `queryClient.invalidateQueries({ queryKey: ['dsa', ...] })` runs, refetching fresh data from the server.
   - `toast.success('Attempt logged!')` displays a transient success notification.

## 4. How Authentication & Silent Token Refresh Work

Placement Copilot implements a secure **Dual-Token Architecture**:

| Token Type | Storage Location | Lifetime | Purpose |
| :--- | :--- | :--- | :--- |
| **Access Token** | Memory (`ApiClient.accessToken`) | 30 minutes | Authorizes API requests via `Authorization: Bearer` header. |
| **Refresh Token**| HTTP-Only, Secure, SameSite Cookie | 7 days | Rotated transparently to issue fresh access tokens without re-login. |

### 1. App Startup (Session Hydration)
When the user opens the application:
1. `App.jsx` executes an initial `useEffect` triggering `useAuthStore.getState().checkAuth()`.
2. `checkAuth()` sends `POST /api/v1/auth/refresh` with `credentials: 'include'`.
3. If the browser holds a valid `refresh_token` cookie:
   - Backend returns a new `access_token` and user profile payload.
   - `ApiClient.setAccessToken(token)` stores the token in memory.
   - Zustand updates `isAuthenticated = true` and `isLoading = false`.
4. If no cookie exists or the session is revoked:
   - Zustand sets `isAuthenticated = false` and `isLoading = false`.
   - `ProtectedRoute` renders a redirect to `/auth`.

### 2. Silent Token Refresh on 401 Unauthorized
When an access token expires during active user activity:
1. Any in-flight API call returns `HTTP 401 Unauthorized`.
2. `ApiClient.request()` catches the 401 (ignoring `/auth/*` endpoints).
3. If no refresh is currently active (`!this.isRefreshing`):
   - Sets `isRefreshing = true`.
   - Calls `POST /api/v1/auth/refresh`.
   - Upon receiving a fresh token, calls `setAccessToken(newToken)` and notifies all waiting callers via `onTokenRefreshed(newToken)`.
   - Retries the initial failed request with the new `Bearer` token.
4. **Thundering Herd Protection (Queued Requests)**:
   - If other requests fail with 401 while a refresh is *already* in flight, they are not dropped.
   - They register callbacks via `addRefreshSubscriber(cb)`.
   - When the primary refresh finishes, all queued requests resolve their retry promises concurrently with the new token.
5. **Terminal Expiry**:
   - If `tryRefreshToken()` returns null (e.g., refresh cookie expired or invalidated), `window.dispatchEvent(new CustomEvent('auth:expired'))` fires.
   - `authStore.js` catches this event, cleans up client auth state, and prompts the user to log in again.

## 5. Where State Lives: Zustand vs TanStack Query

State in Placement Copilot is cleanly segmented based on longevity, locality, and source of truth:

### 1. Server State (`TanStack Query`)
All data that originates on the server and is subject to asynchronous changes is managed by TanStack Query.
- **Why**: Eliminates manual loading spinners, race conditions, stale cache bugs, and boilerplate fetch effects.
- **Examples**:
  - `['dashboard', timeRange]`: Placement readiness composite scores, component breakdowns, levers.
  - `['dsa-topics']`, `['dsa-attempts']`, `['dsa-mastery']`: Coding attempts and topic progress.
  - `['resumes']`, `['ats-analyses']`: Uploaded resumes and match reports.
  - `['interviews']`, `['interview-report', id]`: Adaptive mock interview sessions.

### 2. Global Client State (`Zustand`)
Data that is strictly client-side, synchronous, and needed across multiple unrelated components lives in Zustand stores.
- **Why**: Ultra-lightweight (under 1KB), zero provider boilerplate, subscribable outside of React component trees (e.g. inside `ApiClient` or event listeners).
- **Stores**:
  - `useAuthStore` (`src/features/auth/authStore.js`): `user`, `accessToken`, `isAuthenticated`, `isLoading`, `login()`, `register()`, `logout()`, `checkAuth()`.
  - `useToastStore` (`src/components/common/toastStore.js`): `toasts`, `showToast()`, `removeToast()`, `toast.success()`, `toast.error()`.

### 3. Local UI & Form State (`React useState` & `react-hook-form`)
- **React Hook Form**: Manages transient input state, dirty states, and client-side Zod validation for forms (e.g., login credentials, logging a DSA problem, pasting a job description).
- **React useState**: Micro-UI states such as active tab, search filter query, modal open/close toggles, and dropdown visibility.

## 6. Interview Quick Reference

| Question | Short Answer |
| :--- | :--- |
| **Why pure JavaScript / JSX?** | Simplicity, readability, and immediate understanding without compilation or typing friction during technical interviews. |
| **Where are tokens stored?** | Short-lived Access Token in memory; Refresh Token in HTTP-Only, Secure cookies to prevent XSS exfiltration. |
| **How is concurrent request refresh handled?** | With a subscriber queue in `ApiClient` that prevents duplicate refresh calls ("thundering herd"). |
| **Why TanStack Query over Redux?** | 90% of app state is server state (caching, invalidation, loading flags). TanStack Query solves this natively without Redux reducers and actions. |
| **How are routes protected?** | `ProtectedRoute.jsx` checks `useAuthStore((s) => s.isAuthenticated)`. If false, renders `<Navigate to="/auth" replace />`. |
